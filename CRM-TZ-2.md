# ТЗ, заход 2: каталог товаров, продажа с моделью, быстрая трата

Задание для агента-исполнителя. Продолжение `CRM-TZ.md` (этап 1 принят и на боевом). Все правила, границы и стандарт отчётности из `CRM-TZ.md` действуют полностью.

## 1. Каталог товаров с вариациями (конструктор)

Данные: `catalog/catalog.json` — 172 реальные позиции BORZO из Kaspi, уже нормализованные. Структура item: `{code, name, size, ntin, cat, base, corpus, legs, len, width, line, mod}` + `legend` (расшифровки цветов/линеек).

### Модель данных
- `crm_cat_models`: базовая модель (id, type «Стол/Консоль/Тумба/Банкетка/Пуф/Столик», series+base, name, line, ord, archived).
- `crm_cat_options`: настраиваемые СЛОВАРИ опций (kind: 'corpus' | 'legs' | 'len' | 'width' | другое-добавляемое, value, ord). Всё добавляемо/редактируемо «плюсиком» — как конструктор: появилась новая модель/цвет — mgr добавляет сам, без программиста.
- `crm_cat_variants`: конкретная комбинация (model_id, corpus, legs, len, width, code, ntin, link, price NUMERIC NULL, archived). Код/NTIN редактируемы; вариант можно добавить вручную (для позиций, которых нет в Kaspi-файле).
- Цен в источнике НЕТ — поле price пустое, проставляется в интерфейсе карточки модели/варианта.

### Сидинг
Разовая загрузка `catalog/catalog.json` при инициализации (или POST /api/crm/catalog/seed, mgr, идемпотентно по code): создать модели, словари опций из legend + фактических значений, варианты. Повторный запуск ничего не дублирует.

### Экран «Каталог» (вкладка в crm.html, mgr и fin)
- Список моделей по типам, поиск. Карточка модели: опции, таблица вариантов (корпус × ножки × размер), цена у варианта, код/NTIN.
- «+ Модель», «+ вариант», «+ значение опции» (стиль плюсиков как в финансах). Редактирование и архив (не удаление — на вариант могут ссылаться сделки).

## 2. Продажа = конкретный товар

- В сделке items выбираются ИЗ КАТАЛОГА: тип → модель → корпус/ножки/размер → qty. Цена подставляется из варианта (если задана), редактируема. Свободная строка «прочее» остаётся как fallback.
- Перевод в «Выполнено»: состав обязателен (уже так) и теперь привязан к вариантам каталога (variant_id в items JSONB).
- К сделке прикладывается документ продажи (фото/PDF, «документ Kaspi» — там всегда QR): использовать существующий механизм файлов, но выделить кнопкой «📎 Документ оплаты» в форме won. Не обязателен (не блокирует), но подсвечивать сделки без документа.
- В карточке сделки состав показывать по-человечески: «Стол LUX 3 м · корпус Белый · ножки Gold × 1».

## 3. Быстрая личная трата (вне CRM, для Руслана)

Новая мини-страница `app/quick.html` (+quick.js): одна форма — сумма (крупный ввод), категория (чипы из личных категорий Руслана), опц. заметка, кнопка «Списать». Пишет операцию личного расхода Руслана (kind:'out', acc:'zpRuslan', project:'Личное') НАПРЯМУЮ в fin_state через СУЩЕСТВУЮЩИЙ безопасный путь: GET /api/fin → добавить op → PUT /api/fin с baseRev (конфликт → перечитать и повторить, до 3 раз). Никаких новых таблиц.
- Требует логина (роль mgr); без токена → login.html?next=quick.html.
- PWA: manifest-иконка «Трата», чтобы добавить на главный экран отдельной кнопкой. После сохранения — короткое «✓ Записано» и форма очищается.
- Категории — те же, что в личном кабинете финансов (хранятся в fin_state.cats), новые добавляются плюсиком и видны в финансах.

## Критерии приёмки
1. Seed каталога: 46 моделей / 171 вариант из JSON, повторный запуск — 0 дублей.
2. mgr добавляет новую модель + новый цвет корпуса + вариант с ценой ТОЛЬКО через интерфейс (без кода) — появляется в выборе состава сделки.
3. Сделка: состав из каталога, цена подтянулась, won с documento Kaspi прикреплён; в ленте видно человекочитаемый состав.
4. Архив варианта не ломает старые сделки (состав показывается по сохранённому снимку названия).
5. quick.html: от открытия иконки до записанной траты — 2 действия (сумма → Списать); операция видна в финансах в Личных Руслана, баланс сходится; конфликт версий не теряет запись.
6. Касса/финансы/склад: существующие данные и маршруты не изменились (снимки до/после идентичны).
7. XSS: названия моделей/опций экранируются везде.

## Не делать
WhatsApp, производство/отгрузки, Meta — следующие этапы. Дизайн-полировку не делать: механика важнее красоты (слова владельца).
